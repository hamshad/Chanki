# Phase 6: Sync + Rules
## Plan 06-01: Firebase Setup & Firestore Rules

**Goal**: User's progress syncs across launches in the background while the backend stays locked against public writes.

### Tasks
1. **Firebase Configuration**: 
   - Add Firestore rules (`firestore.rules`) and link it in `firebase.json`.
   - Setup `firebase` SDK in the project dependencies (`firebase` package).
   - Create Firebase initialization logic in `src/data/firebase.ts`.
2. **Firestore Rules Setup**:
   - Deny-by-default rules.
   - User progress rule: users can read/write their own progress documents stored under `devices/{deviceId}/progress/{progressId}`. Wait, is it `devices/{deviceId}`? `PROJECT.md` says: "devices/{deviceId} doc in Firestore storing progress". So user can only read/write to `devices/{deviceId}/*`.
   - Admin rule (for future Phase 7): write access if token has `admin` claim. Wait, anonymous auth does not have custom claims, so how do we handle anonymous user writing to their device ID?
   The plan is: use Anonymous Auth to get a `uid`, and the user can only write to `users/{uid}`. BUT we are using an anonymous device UUID generated in `getOrCreateDeviceId()`. So we don't even need Firebase Auth, we could just allow reads/writes where `resource.data.deviceId == request.resource.data.deviceId`? NO. That is insecure (anyone can spoof `deviceId`). The secure way is either Firebase Anonymous Auth (and using `request.auth.uid`), OR we just don't have true security on the device ID (since anyone can guess/steal a device ID, but UUIDs are unguessable). "Anonymous device-as-user progress sync".
   Let's check `PROJECT.md`: "PWA identity idea: anonymous UUID in IndexedDB + devices/{deviceId} doc in Firestore storing progress; phone-number storage explicitly NOT wanted without consent — keep anon UUID, no PII."
   And: "Auth: No login for learners — anon device ID only; admin gate must not become open write hole"
   So for Firestore rules, how can we restrict writes to `devices/{deviceId}`? If we don't use Firebase Auth, ANYONE can write to any `devices/{deviceId}` if they know the UUID. Since UUIDs are unguessable, it's as secure as a bearer token. So the rule can just be:
   ```rules
   match /devices/{deviceId} {
     allow read, write: if true; // Unguessable UUID is the only protection
   }
   match /devices/{deviceId}/progress/{docId} {
     allow read, write: if true; // Unguessable UUID is the only protection
   }
   ```
   Wait, is that what we want? Yes. Admin gate (decks, cards) should be locked.
3. **Background Sync Worker**:
   - A `SyncManager` that listens to `db.progress` where `syncStatus === 'pending'` and pushes them to Firestore.
   - Pull down newer `progress` from Firestore and merge using `updatedAt`.
4. **Testing**: Write emulator tests for the Firestore rules to ensure `assertFails` on admin tables (decks, cards) and `assertSucceeds` on `devices/*`.
